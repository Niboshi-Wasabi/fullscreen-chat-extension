# 要件整理

## 使用条件

新しい機能要求、既存仕様の矛盾、受け入れ条件が曖昧な依頼。既に確認済みの情報を重複質問しない。

## 参照資料

[文書索引](../../../docs/index.md)、[PRD](../../../docs/prd.md)、[問題台帳](../../../docs/quality/issues.md)、変更する領域のコードと正本。

## 入力

ユーザーの依頼、既に確認した回答、対象サイト・モード、関連課題。入力不足でも読み取り調査は進める。

## 手順

1. 目的・対象ユーザー・対象/対象外を既存要件と照合する。
2. 要求、コード上の挙動、未検証事項を分ける。関連経路を確認する。
3. 設計判断に必要な曖昧性だけを質問し、依存しない調査を続ける。
4. 期待する観測結果、ブラウザ差、失敗時、検証方法を受け入れ条件として整理する。
5. 承認済みの変更だけを正本へ反映し、未決定事項は継続して参照できる課題 ID で記録する。

## 制約

PRDの凍結条件を守る。権限・通信先・性能数値を独断で確定しない。要件整理の依頼を実装・外部操作の許可に拡張しない。読み取り専用の依頼なら文書も変更せず提案を返す。

## 完了条件

確認済み要件と未決定を区別し、次の作業の前提が明確。回答待ちなら要件確定とは報告しない。

## 出力形式

要件差分、受け入れ条件、未決定事項と判断が必要な時点、影響する正本・課題ID、次の作業。

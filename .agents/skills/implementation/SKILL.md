# 実装

## 使用条件
コード・設定・テスト・開発ハーネスの変更依頼。独立レビューでは使用しない。

## 参照資料
[作業フロー](../../../docs/quality/workflow.md)、[コード原則](../../../docs/quality/code-principles.md)、[構造](../../../docs/architecture/overview.md)、[品質基準](../../../docs/quality/standards.md)、関連計画・仕様。

## 入力
許可された範囲、要件/課題、既存差分、計画。小変更でも目的と受け入れ条件を確認する。

## 手順
1. 現在ブランチ・作業先・既存変更を確認し、新規機能・リファクタリング・修正では最新の `main` から切った機能単位の `feature/<機能名>` ブランチ上にあることを確かめたうえで（[作業フロー](../../../docs/quality/workflow.md#ブランチとpr運用)）、変更経路と仕様を読む。影響する未決定は確認する。
2. 最小限の変更を行い、保存互換性、資源解除、ブラウザ境界を維持する。
3. 挙動を変える場合は、その変更を確かめられる回帰検証を追加する。テスト環境が未導入なら、その旨を記録する。実サイト由来なら [regression-from-live.md](../../../docs/quality/regression-from-live.md) に従い匿名 fixture・リンク台帳・両面確認（合成＋可能なら実サイト）を残す。
4. 正本と計画を更新し、影響する検証を実行する。
5. 自己確認後、対象と証跡を独立レビュー担当へ渡す。指摘を修正し再検証する。
6. PR マージまで実施した場合は `pnpm.cmd check:release:drift` で GitHub Release との乖離を確認し報告する。

## 制約
`main` ブランチへの直接編集・直接マージ、無関係な変更、既存作業の破棄、無断の依存追加・権限緩和を避ける。費用、コミット、push、PR 作成・マージ、タグ作成、Release 公開・ストア提出は許可範囲に従う。自己確認を独立レビューと呼ばない。

## 完了条件
要求と差分が一致し、検証と残課題が明確。独立レビュー・人間の判断が未実施ならマージ/公開可能とは報告しない。

## 出力形式
変更点と理由、対象ファイル、検証コマンド/結果、失敗・未検証、レビュー待ち、残課題。

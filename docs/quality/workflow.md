# 実装・独立レビュー・人間の判断

## 役割

| 役割 | 標準ツール | 責務 |
|---|---|---|
| 実装担当 | Cursorを主に利用 | 要件整理、設計、計画、実装、テスト、文書更新、指摘修正 |
| 独立レビュー担当 | Codexを主に利用 | 別セッションで仕様・差分・関連コード・検証を直接調査 |
| 人間 | プロジェクトオーナー | 未確定事項、仕様・権限・費用、最終マージ・公開を判断 |

製品名は固定の権限ではない。依頼が実装ならCodexも実装を行える。実装担当の自己確認は独立レビューではない。

レビュー担当は明示的な修正許可がなければソース・設定・テストを変更しない。指摘と証跡を返し、実装担当が修正する。修正許可を受けて自ら変更した部分は、さらに別の担当による確認が必要。

## 作業の流れ

1. 要件の正本・関連コード・[問題台帳](issues.md)を確認。矛盾する要求を独断で確定しない。
2. 新規機能開発・リファクタリング・不具合修正を始める前に、最新の `main` から機能単位の `feature/<機能名>` ブランチを作成する。既存の未コミット変更が別作業として残っている場合は、混在や破棄をせず扱いを人間へ確認する。
3. 複数モジュール、契約・権限・保存形式・基盤を変える作業は[計画](../plans/TEMPLATE.md)を保存。重要判断はADRを記録。
4. 人間の判断が必要な点を具体化して提示。既に認可された範囲の通常作業に重複承認を要求しない。
5. 実装し、影響する回帰と文書更新を行う。
6. [品質基準](standards.md)に従い検証。未導入の検証を成功と記録しない。
7. 独立したレビュー担当が対象全体を調査。実装担当の報告だけで結論を出さない。
8. 実装担当が指摘を修正し、再検証。レビュー担当は変更された対象と関連経路を再レビュー。
9. Critical / Major / Minorがなく、必須検証が完了してから、人間が対象を確認。
10. 明示的な許可を得て `feature/<機能名>` ブランチへコミット・pushし、`main` 宛てのPRを作成して必須CIと本人確認のうえでマージする（`main` への直接push・直接マージは行わない）。許可の範囲を拡張しない。

小さい変更も最終確認は行う。純粋な文言修正は短い正確性確認でよいが、同時に変えたコードのレビューを省略しない。検証はレビューの前後で必要な時点に行い、不合格のまま完了にしない。

レビューは正しさ・安全・保守性・性能を優先し、フォーマッターが扱うスタイルだけの指摘に偏らない。指摘対応後は更新対象を新たな視点で一通り読み直し、関連ファイルを含む最終確認まで行う。途中の確認を最終レビューの代わりにしない。

## 仕様変更

要求と実装の差を台帳に記録し、期待する動作・理由・代替案・影響を提示する。PRDの既存凍結条件に従い承認された変更だけを正本へ反映し、改訂履歴、関連契約、計画、検証を更新する。テストを通すために要求を変更しない。

## レビューと証跡

[レビュー書式](review-template.md)を使う。レビューは比較元・対象コミットに結び付ける。レビュー後の差分は影響を再確認する。Git未配置中は対象ファイル一覧とSHA-256、差分を利用し、コミット識別やPR保護と同等とは扱わない。

検証ログ・画像からチャット本文、ユーザー識別子、認証情報を除去する。CI生成物はリポジトリへ丸ごと保存せず、計画・PRに必要な証跡への参照を残す。

## ブランチとPR運用

新規機能開発・リファクタリング・不具合修正は、常に最新の `main` から機能単位の `feature/<機能名>` ブランチを切り分けて進め、`main` 上での直接作業・直接コミット・直接マージを禁止する。1 ブランチ・1 PR は 1 つの目的（機能またはリファクタリング）に絞り、関連しない変更を混在させない。

`main` への統合は、作業ブランチを push して [PRテンプレート](../../.github/pull_request_template.md)に沿った PR を作成し、必須 CI・独立 AI レビュー記録・本人の最終確認を通過したうえで PR マージで行う。本人は自分の PR へ別人の承認を付けられないため、利用できない承認条件を必須にせず、CI は人間の判断や AI レビューの意味的な正しさを保証しない前提で扱う。

CI ファイル・`main` ブランチ保護・初回実行は整備済みであり、詳細設定は[CI手順](../operations/ci.md)を正本とする。自動チェックだけでストア提出は行わない。

## 継続改善

再発・検証漏れ・古い文書・過剰な手順を問題台帳へ記録する。影響に比例した回帰テスト、静的制約、文書修正を選ぶ。導入後に有効性と所要時間を評価し、不要なルールやSkillを削減する。

# 実装原則

既存Cursorルールの製品非依存な原則の正本。UI固有の原則は[デザイン](../design/README.md)、検証は[品質基準](standards.md)を参照する。

## 変更を決める前に

- 関連する経路全体を調べ、共通原因を呼出元の個別パッチで隠さない。
- 既存ヘルパー・プラットフォーム機能・導入済み依存を再利用する。
- 未使用の抽象化、要求されていない機能や依存を追加しない。理解したうえで最小の正しい変更を選ぶ。
- 意図的な簡略化には適用限界と次の手段をコメントで残す。

## 構造と表現

- 既存の言語・インデント・命名慣習を守る。小さく単一責務の関数・型を優先する。
- 公開型の役割が新しい保守担当にも把握できる構造・説明にする。
- 未使用import・死んだコード・コメントアウトした残骸を残さない。
- ガード節と共通処理を使い、重複と深い入れ子を抑える。
- 依存を明示し、暗黙の検索や実行環境に隠れた依存を作らない。
- 意味のある定数・設定名を使う。単文字名はごく小さいループに限り、不透明な略称を避ける。
- 真偽値はis / has / should / canなどで意図を示し、ホスト言語の慣習に合わせる。
- 非自明な意図・プロトコル・ブラウザ固有事情は隣接する日本語・英語コメントで記述する。
- 公開APIは目的・入出力・副作用を説明し、コードの逐語説明を増やさない。

## 信頼境界・失敗・ライフサイクル

- 未信頼入力は境界で検証し、安全なプラットフォームAPIを使う。副作用の前に権限と宛先を確認する。
- 内部エラー・スタック・内部識別子・秘密情報を外部へ返さない。ログは診断に必要な範囲に絞る。
- 期待される失敗は呼出側が処理できる形にし、予期しない失敗を握りつぶさない。
- start / stop、購読 / 解除、open / closeを対にする。途中失敗・複数回停止でも資源を残さない。
- 任意APIの不在でクラッシュさせない。代替動作と説明を整合させる。
- 既定値は安全側とし、設定コメントとREADMEを実際の動作に合わせる。

新たなルールは実際の再発や有効性を根拠に提案する。単発事例から全作業の負担を増やさない。

# Firefox MCPと検証ハーネスの接続案

状態: **第1〜第3段階実装済み（2026-11-19）。CI必須化は未実施。**

## 目的・背景

Firefoxでの探索的な実サイトデバッグを、再実行可能な回帰と証跡へつなぐ。CursorへのMCP接続、拡張の動作、検証完了をそれぞれ区別する。Chrome も同じ `results.json` 形式で記録する。

現状:

- [接続記録](../quality/firefox-devtools-mcp-2026-11-18.md)では一時クライアントの操作は成功したが、Cursor自身からのツール呼び出しは未確認。
- [verify.mjs](../../scripts/verify.mjs)のブラウザ選択はChromium／Chromeのみ。
- [Firefox既存記録](../quality/firefox-verification-2026-11-15.md)にはBiDiによる合成検証があるが、ランナーはローカル成果物領域にあり、常設コマンドではない。廃止機能も含むため、そのまま現行の保証には使えない。

## 対象範囲・対象外

対象は検証基盤・手順・結果の関連付け。製品の権限・通信先・保存形式・PRDは変更しない。通常プロファイルの利用、無許可の実投稿、OSの保護設定変更は対象外。

## 設計

1. **共通の準備と証跡**: ビルドとファイルハッシュ、ブラウザ／MCP版、実行ID、対象コミットと未コミット差分の識別、プロファイル、設定条件を記録する。ビルド後に読み込んだ出力との対応も確認する。既存成果物を上書きせず実行ごとに保存する。
2. **MCP実サイト確認**: 既存の[実サイトチェックリスト](../quality/site-verification-checklist-2026-11-15.md)の項目IDを使い、期待値・操作・観測・判定・証跡を記録する。手順や受け入れ条件を別の正本へ複製しない。動的な配信状況で確認できなければ未検証とする。
3. **自動回帰**: MCPで見つけた問題を匿名化したfixtureと決定的なアサーションへ移す。既存のChrome E2E・単体／結合を再利用し、Firefox固有問題にはインストール済みFirefox＋BiDiの合成回帰を用意する。AIの自由な操作を通常CIの合否判定にしない。

実行環境は `synthetic` / `live-site`、実行主体は自動アサーション / エージェント / 人間を区別する。結果は成功・失敗・未実行・実行不能・対象外を区別し、根拠や理由を必須にする。ツールの起動失敗を製品の不具合と混同しない。証跡不足の成功記録は受理せず、JSONの形式検査自体を機能合格と扱わない。

認証情報・チャット本文・視聴者識別子を成果物から除去する。実サイトの画像・ログは合成E2EのCIアップロード対象に混入させない。

## 実装手順

### 第1段階: 実サイト結果を既存ハーネスへ関連付け

- CursorからMCPを呼び出せることを確認する。
- ビルド識別と実行単位の証跡保存を用意し、既存チェックリストの項目IDに結果を関連付ける。
- 結果JSONを検査する小さいスクリプトを追加する。対応する実行記録・ビルド識別・証跡の存在と判定理由を確認する。
- [ブラウザ手順](../operations/browser-verification.md)・[品質基準](../quality/standards.md)・[デバッグ手順](../operations/debugging.md)から案内する。通常verifyの実行範囲はこの段階では変えない。

### 第2段階: Firefoxの常設合成回帰

- 既存ローカルBiDiランナーの存在・実装を調査し、現行要件に有効な部分だけ再利用する。成果物の存在だけで導入済みとしない。
- まず起動、一時拡張読み込み、合成受信、OFF/ON、終了を最小構成で常設化する。プロファイル所有権と後始末を保証する。
- Firefox固有の起動制御をPlaywrightのChrome fixtureへ無理に押し込まない。共有できるfixture・期待値・結果形式から再利用する。
- 必要な依存・実行時間・対応環境を提示してから、Firefox用の明示的コマンドを追加する。既存のverify／CIへの必須化は別判断とする。

### 第3段階: 発見から再発防止へ

- 実サイトの再現条件を台帳へ記録し、匿名化fixtureによる回帰を追加する。
- 修正後は合成回帰と該当する実サイト項目の両方を確認する。配信やログイン条件が揃わない場合は、実サイト再確認待ちを残す。

## リスク・判断点

- MCPは現在 `@latest` 設定。再現性のため、動作確認した版と起動構成を記録し、更新方針を決める。既存の Cursor 設定を上書きするには事前に確認する。
- 実サイトは配信終了・コメント不在・認証・DOM変更に影響されるため、通常verifyに必須化すると外的要因で不安定になる。
- フルスクリーン・IME・Document PiPはスタブやDOM存在だけでは合格にしない。
- 新しい依存、CIへの追加、プロファイルの長期保存方針は実装時に影響を提示する。

## 検証方法・完了条件

第1段階は、Cursor自身の接続確認、実行とビルドの識別、既存項目IDと証跡の対応、および証跡欠落・未知ID・不正判定等を拒否する負例の確認で完了とする。機能の未検証項目は残せるが、すべて合格とは報告しない。

第2段階はクリーンな専用プロファイルでFirefox合成回帰をコマンドから再実行でき、機能失敗・起動失敗で非ゼロ終了し、証跡と後始末を確認できることを条件とする。ハーネス変更には通常verifyと対象ブラウザ確認を適用する。独立レビューと公開判断は別条件。

第3段階は、リンク台帳と `check:regression-links` で ISS・checklist・合成テストの対応が機械検証でき、手順書どおり両面確認（合成＋実サイト再確認の区別）が残ることを条件とする。pending の liveRecheck を失敗扱いにはしない。全実サイト項目の消化や CI 必須化は含めない。
